Engineering Patram 1.5

Serving training data from local disks

The storage layer behind Patram 1.5's training

Training a vision-language model means reading tens of millions of small images and records, many times over. Patram-FS packs them into a few hundred large shards, downloads each shard once onto every machine that needs it, and lets every process on that machine read any sample straight from the local disk by its byte address.

01 The problem

Reading tens of millions of small files

A training sample is a small file. A dataset holds tens of millions of them, and every GPU on the cluster reads them over and over.

Patram 1.5 learns from document images and the text that goes with them: an image of a page, and an annotation that says what is on it, such as a transcription, or a question about the page and its answer. An image is 50 to 500 KB. An annotation is a JSON record of about 300 bytes. A training dataset holds tens of millions of both.

The simplest way to store them is one file per sample, and the simplest way to train on them is to open each file when it is needed:

for path in sample_paths:
    image  = load_image(path + ".jpg")
    record = json.load(open(path + ".json"))
    train_step(image, record)

That works for a thousand files. Our cluster has 30 machines with 8 GPUs each, and every GPU is fed by several reader processes, all opening different small files as fast as they can. At ten million files, three things go wrong.

  1. The shared filesystem slows down for everyone. A shared network filesystem keeps a metadata entry for every file, and it slows down with the number of files, whatever their size. At ten million files, listing the dataset folder takes minutes, and the metadata load slows every other machine on the cluster.
  2. The object store limits requests, not bytes. Datasets live long term in an object store (we use Amazon S3). It allows roughly 5,500 requests per second for each prefix, and a run that fetches samples one at a time makes about ten million requests against that limit.
  3. Processes on one machine repeat each other's work. A machine runs several processes that read the same data, such as training, a data job and someone's notebook, and each one fetches its own copy.

Patram-FS solves these in order. The rest of this post builds it up one step at a time. Five terms come up throughout:

Machine
One server in the GPU cluster, also called a node. Ours each have 8 H100 GPUs and a 30 TB local drive, and the cluster has 30 of them, 240 GPUs in all.
NVMe
That local drive, attached directly to the machine. Reads take tens of microseconds, against milliseconds for anything that crosses the network.
Shared filesystem
A network filesystem that every machine mounts, so every machine sees the same files. It keeps a metadata entry (an inode) for every file.
Object store
Where datasets live long term, such as Amazon S3. Data is read and written as whole objects over the network, and it charges and limits by request.
Worker
A Python process that reads training samples, for example a data loader worker. A machine runs dozens of them, and nothing coordinates them with each other.

02 Shards

Packing samples into shards, and keeping each sample's address

Fewer, larger files solve the file-count problem. The question is how to pack them so one sample can still be read on its own.

The standard fix for too many small files is to pack them into a few large archive files, called shards. We pack images into TAR files of about 10 GiB each, and annotations into JSONL files (one JSON record per line) of about 1 GiB each. A dataset of tens of millions of samples becomes about two hundred shards.

The important choice is that the shards are not compressed. In an uncompressed TAR file, every image sits at a fixed byte position, so reading one image is one seek and one read, with nothing to unpack. Compression would barely help anyway: the images are already compressed JPEGs, and compressing them again saves 0 to 2%. Without it, building a shard is plain copying, at 1 to 2 GB per second.

So every sample has an address: the shard it lives in, the byte where it starts, and its length.

We write the address as a short link: patram://img/000123?shard=…&offset=…&length=…. It contains everything needed to read the sample. No index has to be loaded and no service has to be asked, so an address can go anywhere a file path used to go: a list of samples, a config file, a column in a table.

That is what keeps existing code working. Our data pipelines, training loops and evaluation scripts were all written for "each sample is a file at a path". Give each sample an address instead of a path, and the code keeps its assumption. Only the read call changes:

read_image and read_annotation are the whole client interface, because an image plus a JSON record is the shape of all our training data. The library also has build_uri and parse_uri for making and checking addresses when you build a dataset.

The promise behind those two calls is simple: calling code reads an address as if the shard were already a file on the machine's local drive. The rest of this post is about how the library and a small program on each machine make that true.

Ids instead of addresses

Carrying the full address everywhere is not compulsory. You can keep a database table that maps each record id to its shard, offset and length, and pass a short record_id around instead. The physical layout is then free to change without touching any list of samples.

The problem with a shared database

A hundred workers on a machine, each looking up ids on its own, means a hundred database connections and a hundred separate queries, many of them for rows a neighbouring worker just fetched.

What the daemon does

The per-machine daemon introduced below does the lookup instead. Workers send it ids, and it gathers the requests that arrive together into one query, so the database sees one client per machine instead of one per worker.

Batching without a timer

The usual way to batch is to wait a few milliseconds and send whatever has arrived. That adds the wait to every lookup, even on an idle machine. The daemon has no timer. It keeps up to 8 queries in flight. A request that arrives when a slot is free goes out at once, as a batch of one, in about 1 millisecond. Requests that arrive while all slots are busy pile up and go out together the moment a slot frees. Under load, 128 lookups arriving together resolve in two or three database round trips instead of 128.

03 Local cache

Caching shards on each machine's local disk

Fetching from the object store on every read would bring the request problem back. Each machine keeps the shards it uses on its own disk.

Every machine in our cluster has a 30 TB NVMe drive attached directly to it. Reading from it takes tens of microseconds, against milliseconds for anything that crosses the network. So the first time a machine needs a shard, it downloads the whole shard from the object store to its local drive. From then on, every sample in that shard is a local read.

A download is written to a temporary file and renamed into place only when it is complete, so a reader never sees a half-downloaded shard.

This creates the next problem. A machine does not run one process. It runs eight training processes, one per GPU, each with several reader processes, and often a data job or a notebook next to them. They start at the same moment, they read the same shards, and they know nothing about each other.

If each one downloads a shard whenever it finds it missing, the machine downloads the same 10 GiB shard many times over. An earlier design of ours did exactly that: 16 reader processes missing the same shard caused 16 separate downloads.

The problem

Every process on a machine has to turn a shard's location in the object store, such as s3://bucket/images/shard_0042.tar, into the same local file name, without asking anyone. The usual answer is to hash the location and use the hash as the file name.

Why not a hash

A hash makes two locations sharing a name unlikely, not impossible. If it ever happens, the cache serves one shard's bytes under another shard's name. Training then reads the wrong images with no error at all, which is about the worst thing a cache can do.

What we do instead

We encode the location with percent-encoding, the same scheme URLs use, and we also encode the % character itself. That makes the mapping reversible: two different locations can never produce the same name, and given any file in the cache, you can work out exactly which object it came from, with no lookup table and no program running. Names longer than the 255-byte limit for a file name are split into nested folders, always at the boundary of an encoded character.

A mistake we caught

Our first sketch replaced :// with ___ and / with __. It looked fine, but it was not reversible: a://b and a/_b both become a___b. Proper escaping removes that whole class of bug.

04 The daemon

One daemon per machine

A single small program on each machine handles every missing shard, so a shard is downloaded once, however many processes want it.

Each machine runs one Patram-FS daemon: a small background program, written in Go, that runs all the time. Every process on the machine, whether training, a data job or a notebook, talks to the same daemon through a Unix domain socket, a channel between processes on one machine that goes only through the kernel, with no network in the way.

The socket is quick. From Python, a round trip takes a median of 74 microseconds, and 20 processes together pushed 124,000 requests per second through it.

When a process needs a shard that is not on the local disk, it sends the daemon an ensure_shard request. The daemon checks the disk and starts a download only if the shard is not there and is not already downloading. Any other process that asks for the same shard during the download waits for that same download, and they all continue together when it finishes.

We measured this with 20 processes asking for the same missing 1 GiB shard at the same instant. The daemon made one download, and all 20 processes had the shard in 2.16 seconds, the time a single process takes on its own. Asking for a shard that is already on the disk takes under 100 microseconds.

The daemon never handles the data itself. It answers one question, "is this shard on the local disk, and where?", and the process then reads the bytes on its own. So the daemon cannot become a bandwidth bottleneck, and restarting it cannot break a read in progress, because each reader holds its own open file.

Having one daemon per machine also gives every machine-wide question one place to be answered: how hard to hit the object store, what is already cached, how many bytes this machine has downloaded today. Every daemon publishes these numbers as Prometheus metrics, so the whole cluster reads as one Grafana dashboard.

05 Reading

Reading without asking the daemon

Once a shard is on the local disk, reading a sample from it should cost no more than reading an ordinary local file.

A process does not ask the daemon before every read. Because cached shards are named by a fixed rule, a process can work out where a shard should be on the local disk by itself. It opens that file and reads the sample at its offset with pread, a single system call that reads a given number of bytes from a given position. Only if the open fails with FileNotFoundError does it send ensure_shard to the daemon, and then it tries again.

So for each shard, only the first processes to reach it ever talk to the daemon. Every later read, from every process, for the rest of the run, is an ordinary open and read of a local file.

Each process also keeps a few shard files open (16 of each kind by default), so repeated reads from the same shard skip even the open. In the steady state the file is already open, pread runs, and the daemon is not involved.

There is nothing else on the read path. An uncompressed TAR member needs no decoding of its own, so there is no unpacking, no decompression, no format conversion and no filesystem layer between the drive and your tensor.

The only real wait in the system is the first download of a shard. Because ensure_shard can be called for a shard you have not reached yet, a data loader can fetch the next shard while it is still training on the current one, so even that wait overlaps with useful work.

06 Memory

Reading annotations from memory with the page cache

Annotation reads are tiny and scattered. Served from the drive, they make the drive the bottleneck. Served from memory, they are fast, as long as the machine does not keep a hundred copies.

An annotation shard is a 1 GiB JSONL file holding millions of small records of about 300 bytes each. During training, each worker needs a few records at a time, from scattered places in the file, and every worker on the machine is doing this at once. There are two obvious ways to give the workers their records, and each fails in its own way.

  1. Load the whole file into every worker. Each worker reads all 1 GiB into its own memory and looks records up there. Lookups are fast, but workers cannot share their memory with each other, so 100 workers hold 100 copies of the same file: 100 GiB of memory for 1 GiB of data, and every worker waits for the load before it can start.
  2. Read only the bytes you need, straight from the drive. Keep the file on the local NVMe drive and read just each record's bytes at its offset with pread, the way images are read. Memory use stays small. But every record is a separate trip to the drive, a median of 297.6 microseconds for a 300-byte record. Training makes millions of these reads, all from the same drive, and they queue behind each other. The drive becomes the bottleneck.

What we want is the second approach's small reads, answered from memory, with one copy of the file for the whole machine. Linux already has the piece that makes this possible.

The page cache. Whenever a process reads part of a file, the kernel keeps those bytes in spare memory. The next time any process on the machine reads the same bytes, the kernel answers from memory and does not touch the drive. There is one copy of each piece of the file, shared by every process.

On its own, the page cache fills too slowly here. A scattered read brings in only the small piece of the file around one record, so for a long time most reads still miss and go to the drive.

Warming fixes that. When an annotation shard is first fetched, the client sends the daemon a warm_shard request, and the daemon asks the kernel to load the whole file into the page cache in one call (madvise with MADV_POPULATE_READ). That takes about half a second for 1 GiB. From then on, the workers keep making exactly the same small pread calls, and every one is answered from memory.

This is the best of both worlds. Like the first approach, every read comes from memory, so it is fast. Like the second, each worker reads only the record it needs and keeps no copy of its own, so the machine holds one copy of the file, however many workers there are.

Image shards are never warmed, because reading an image is limited by decoding the JPEG, not by the drive. The deep dive below has the measurements.

JSONL files

Over a full pass of random reads across the 1 GiB JSONL file, with the half-second warm-up counted in, the total time fell from 8.58 to 3.33 seconds. With 8 workers reading at once, throughput rose from 19,846 to 28,060 reads per second, because the workers no longer queue on the drive.

Image shards

Image shards behaved differently. Every warming setting landed within 1.5% of not warming at all. Reading an image takes about 15 milliseconds, and nearly all of that is spent decoding the JPEG, not waiting on the drive. Warming a 10 GiB image shard also takes about 5 seconds. So the daemon uses opposite settings for the two kinds of shard: annotation shards are always warmed, and image shards never are. This is also why 10 GiB image shards are fine: they only ever need to sit on the drive, never in memory.

Warming does not pin the file

Warmed data is not locked in memory. The kernel can drop it whenever it needs the memory, so the daemon trusts a finished warm for only a few seconds and warms the file again on the next request after that.

07 Disk space

Keeping the local disk from filling up

A machine's disk holds whichever shards its jobs are using. When it fills up, the shards asked for least recently are removed.

Each kind of shard has its own space budget on the disk, with an upper mark and a lower mark. When a download pushes a budget over its upper mark, the daemon deletes the shards that were asked for least recently, until usage is back under the lower mark.

Going down to the lower mark, not just under the upper one, leaves room for several more downloads before the next clean-up.

Three details make this safe.

  • Separate budgets. One 1 GiB annotation shard holds the records for images spread across many 10 GiB image shards. If both kinds shared one budget, a run of image downloads could push out the small annotation shard that every process needs.
  • A grace period. A shard that the daemon handed to a process in the last few seconds is never removed, even if that process has not opened it yet. The default is 5 seconds.
  • Deleting under readers is safe. On Linux, deleting a file removes its name at once, but its data stays until the last process that has it open closes it. A process in the middle of a shard finishes normally. A process that opens the shard afterwards finds it missing and asks the daemon again, which is the normal path for any missing shard.

The clean-up runs in the background, so the request that triggered it does not wait for it.

08 A general pattern

A daemon per machine, as a general pattern

The daemon makes all the processes on a machine act like one client, without the processes ever talking to each other.

Nothing outside the daemon knows where shards come from. Everywhere this post says "the object store", it means one download routine inside the daemon. That routine calls rclone, an open-source tool that works with every major object store and with many on-premises storage systems. Moving to a different cloud, or to storage in our own data centre, means changing that one routine. Training loops, data pipelines and every sample address stay exactly as they are.

Images and JSONL records are only the two kinds of data we needed first. The daemon does not care what is inside a shard: it fetches, caches, warms and evicts files.

A shard can hold text, speech audio, video frames or any custom format. A new reader function decides how to turn the bytes at an address into a sample, and each new kind gets its own warming choice, made the way we made it for images and JSONL: by measuring whether reads wait on the drive.

The idea reaches beyond shards. On a busy machine, many processes that know nothing about each other need the same shared things: files from the object store, rows from a database, space on the drive, memory. Left alone, each process fetches, queries and caches for itself, and every shared service sees dozens of separate clients from every machine. Making the processes coordinate directly would mean each one knowing about all the others.

A daemon on each machine avoids both. Each process asks its local daemon, and only the daemon talks to the shared service. Because every request on the machine passes through one place, the daemon can merge identical requests, batch the rest into one query, keep one cache, and limit how hard the machine hits the service.

Patram-FS uses the pattern three times. Requests for the same shard become one download, from any object store. Record lookups from every process become one batched database query. And the drive and the page cache hold one copy of each shard, under one budget, for every process on the machine.

Any shared service that many processes on a machine use in the same way can be put behind a daemon like this one. What keeps it safe is the rule Patram-FS follows throughout: the daemon answers questions and coordinates, and the data goes directly from the drive to the process, so the daemon never becomes the bottleneck.

09 Using it

Using Patram-FS

Three pieces: shards with addresses, a daemon on every machine, and a small Python library.

  1. Build the shards. Pack images into uncompressed TAR files of about 10 GiB and annotations into JSONL files of about 1 GiB, upload them to the object store, and record each sample's address (or its shard, offset and length in a database table).
  2. Run the daemon on every machine. The Patram-FS daemon runs as a container that restarts itself if it stops. One command deploys it across the cluster and sizes each machine's cache budgets to its free drive space.
  3. Install the client library. The patram-fs Python package has no required dependencies; reading images also needs OpenCV and NumPy. Replace each path read with read_image or read_annotation.

Most code only ever calls those two functions. Underneath, the library talks to the daemon with three requests, which you can also send yourself:

To watch it in production, each daemon exports metrics for requests, downloads, bytes downloaded, evictions and cache usage, and alerts fire when a daemon stops responding or its requests start failing.

10 Alternatives

Why we built Patram-FS instead of using an existing tool

This is a niche area with only a few tools, and none of them meets every requirement.

Serving shared training data from object storage to many processes on one machine is a narrow problem, and few tools aim at it. We found five that come close: two dataset libraries, a distributed cache and two filesystems that mount a bucket. We read their documentation and source. Our workload needs five things at once:

  1. One cache per machine, shared by every process. A machine runs training, data generation and notebooks side by side. They do not know about each other, and they read the same shards.
  2. Reads at local-disk speed. An epoch is tens of millions of reads, so nothing should sit between a process and the file on each one.
  3. Plain files. Shards stay ordinary uncompressed TAR and JSONL, so any tool can open them and nothing is converted. Tools with their own format make you pack the whole dataset into that format first, and unpack it again for any tool that cannot read it.
  4. Little to run. The machines are there to train. We did not want a cluster of services running on them.
  5. Every kind of job, with a small code change. Training is not the only reader. Data generation, annotation and analysis jobs and notebooks read the same data, mostly as plain Python that opens a file path. Most existing tools are heavily tuned for the PyTorch DataLoader class. To use one, every codebase of ours that reads this data, whether training, annotation or analysis, would have to be rewritten around its dataset class. That is a large rewrite across many codebases.

Each tool below meets some of these and misses at least one.

On requests. A tool that shows a bucket as a folder turns every file read into an S3 request, and S3 limits requests, not bytes: about 5,500 per second for each prefix. With one file per sample, ten million samples means ten million requests, however good the tool is. Packing the samples into TAR shards, which Patram-FS reads as they are, brings that down to about two hundred.

On FUSE. Our first version of this system was a FUSE mount, and each image read cost 1 to 3 ms, against 50 to 200 µs for a direct read from NVMe. A FUSE-based tool pays that extra hop on every read.

None of these is a poor tool. They were built for other workloads. If one coordinated training job is your only workload, a streaming dataset library is an excellent default, and it gives you things Patram-FS does not, such as shard-aware sampling and exact resumption on a different number of GPUs. If you need one cache shared across machines, or a normal file path that unmodified programs can open, look at Alluxio or JuiceFS.

11 Patram 1.5

Training Patram 1.5 from local disks

Patram 1.5 was trained with its data only in the object store and on each machine's local drive.

Before Patram-FS, training read its data from the cluster's shared filesystem, FSx for Lustre. At the scale Patram 1.5 needed, it was too slow, too small and too expensive:

With Patram-FS, the shared filesystem is off the data path. We trained the 7B Patram 1.5 model on 41 billion tokens across 128 GPUs with its training data in S3 and, once a machine needed a shard, on that machine's local NVMe drive.

Training is not the only reader. Our dataset-construction pipelines install the same library and read records by patram:// address, sharing each machine's cache with whatever training job is running there. That is the reason the design keeps a per-sample address: any code that used to take a path can take an address instead. The training corpus itself was generated by our data pipeline engine, described in the Patram-Ingest post.

12 Where it fits

Where it fits, and the trade-offs we chose

Patram-FS suits one kind of cluster well, and gives up a few things on purpose.

Where it works well

  • Many unrelated processes on one machine reading the same data: training, data jobs and notebooks share one cache.
  • Codebases written for "each sample has its own path", which keep working with a one-line change.
  • Reads at the speed of the local drive, with no filesystem layer, no decompression and no daemon on the read path.
  • Any object store, behind one replaceable download routine.

Trade-offs

  • It is not a filesystem.You cannot list the dataset with ls, and code reads samples by address through two functions instead of opening paths.
  • Sampling needs some shard locality.A sampler that jumps uniformly across every shard defeats the cache: each read can pull down another 10 GiB shard and push out one that is still in use. Reading in a shard-aware order keeps it cheap.
  • It is one more program to run.If a daemon stops, every process on that machine can still read every shard already on its disk, but no new shard arrives until the daemon is back.

13 Takeaways

Key takeaways

  1. Pack small samples into large uncompressed shards, and keep a byte address per sampleThe address is what lets existing code keep working with a one-line change.
  2. Put machine-wide coordination in one process, and keep it off the data pathA daemon that never carries data cannot slow reads down, and one daemon per machine turns de-duplication, rate limits and monitoring into local problems.
  3. Ask only on a missTry the local file first. Once a shard is on the disk, a read is an ordinary local read.
  4. Use the page cache as shared memoryWarm a file once and every process on the machine reads it from memory, one copy for all, with no sharing layer of your own.
  5. Measure each kind of data before choosing defaultsThe same warming step made annotation reads 11 times faster and made no difference for images.
