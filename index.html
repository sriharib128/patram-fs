Serving millions of training samples from packed shards

We train vision‑language models on tens of millions of small images and JSON records. Patram‑FS packs them into about two hundred shards and caches those on each node's local NVMe, so training code still reads every sample as if it were a local file while the storage layer sees about 200 requests per run.

Before we start

Five terms, so the rest reads cleanly

node
One machine in a GPU training cluster. Ours carry 8 H100 GPUs and a 30 TB local SSD each, and the fleet has 32 of them, 256 GPUs in all.
NVMe
That local SSD. Reads land in tens of microseconds, against milliseconds for anything that crosses the network.
inode
The metadata entry a filesystem keeps for every file. A shared filesystem slows down as the count climbs into the millions, whatever size the files are.
object store
Where datasets live long term. We use S3, but nothing here depends on that; any bucket‑style store behaves the same way.
worker
A Python process that reads training samples. A job runs dozens per node, and nothing coordinates them with each other.

01 · The problem

What breaks at ten million files

A vision training sample is small. Our images run 50 to 500 KB and an annotation record is about 300 bytes, but a serious dataset holds tens of millions of both. Store each sample as its own file and every layer of the stack starts charging you for the count instead of the bytes.

The cost shows up in three places. A shared filesystem keeps one inode per file, and at ten million inodes an ls on the dataset directory takes minutes while metadata pressure slows every other node on the cluster. An object store throttles by request rate, around 5,500 GETs per second per S3 prefix, and a run that fetches samples one by one issues about ten million GETs against that ceiling. And each of those reads is its own operating‑system call out of Python.

Put 256 GPUs' worth of dataloader workers on that, each opening a different small file as fast as it can, and shared storage becomes the component that sets the training speed.

02 · Storage layout

Pack the samples, keep their addresses

The standard fix is to pack samples into big archive files, and we do. The choice that matters is which format. We pack images into plain uncompressed TAR and annotations into JSONL, one JSON record per line, and we never compress either.

Leaving the archives uncompressed is what makes the layout work. With no compression, every member of a TAR sits at a fixed byte offset, so reading one image is a single seek and read straight out of the archive, with no unpacking and no index traversal. Building shards runs at 1–2 GB/s because it's pure copying, and since JPEGs are already compressed, gzip would've bought us 0–2% anyway.

Why this matters

Fixed offsets keep every codebase working, unchanged

Our data‑generation pipelines, training loops and eval scripts were all written against "each sample is a file at a path." Hand each sample a byte offset instead of a path and all of that code keeps its assumption. Preserving that per‑sample address is the design's main constraint; the daemon and the cache described below exist to serve it.

Physically, the dataset collapses into about two hundred shards, image TARs around 10 GiB and annotation JSONLs around 1 GiB, where one JSONL still packs a few million records. A training run now touches storage about 200 times instead of about 10 million.

03 · The API

Two functions

A sample's address becomes a URI naming its shard, byte offset and length. The read call changes; the URI carries what the path used to.

beforea path per sample
# each sample is its own file
img_path = f"{root}/img_000123.jpg"
ann_path = f"{root}/img_000123.json"

img = cv2.imread(img_path)
ann = json.loads(open(ann_path).read())
aftera URI per sample
from patram_fs import read_image, read_annotation

img_uri = f"patram://img/000123?shard={path}" \
          f"&offset={offset}&length={length}"
ann_uri = f"patram://ann/000123?shard={path}" \
          f"&offset={offset}&length={length}"

img = read_image(img_uri)
ann = read_annotation(ann_uri)

The URI is self‑describing: shard, offset, length, and nothing else. No index has to be loaded and no service has to be consulted to turn it into bytes, which is what lets a URI travel anywhere a path used to — a manifest, a config, a Parquet column, a log line.

read_image and read_annotation are the entire client surface, because image plus JSON is the shape of all our training data today; a third reader for a new record type is a small patch, not a redesign. The contract behind them is what matters: calling code reads a URI as if the shard were already a file on the node's NVMe. The client library and a per‑node daemon make that true, fetching a shard from the object store the first time a node needs it.

If you'd rather pass record ids than URIs side note

Carrying the full byte range everywhere isn't compulsory. You can keep a database that maps a record id to its shard, offset and length, and then pass record_id around instead — shorter, and the physical layout stays free to change under you.

The catch is the one every shared database has. A hundred workers per node, each resolving ids on its own, is a hundred connections and a hundred redundant queries for rows their neighbours already fetched. So the daemon does that lookup too: workers ask it, it collapses the concurrent asks into one query per node, and caches what comes back. Contention on the database drops by roughly the number of processes you were running.

The same pattern applies to every shared resource here, the object store, the drive, RAM, or a database connection pool: the daemon makes one node's hundred processes behave like a single client.

04 · The daemon

One daemon per node

So what happens when the file isn't there? Each node runs patramd, one small Go daemon. Workers reach it over a Unix domain socket, a kernel‑only channel with no network stack in the way; from Python we measured a median round trip of 74 µs while 20 processes pushed 124,000 requests per second through it.

A worker that misses a file asks the daemon to ensure_shard. The daemon checks NVMe and downloads the shard from the object store only if it's absent. Since every process on the node, training ranks, data jobs, someone's notebook, talks to the same daemon, a node downloads any given shard exactly once.

One daemon per node also gives each operational question one place to be answered. How hard to hit S3, what's already cached, how many bytes this node pulled today, whether object‑store connectivity is failing right now: each has one place to ask and one place to tune, instead of a hundred uncoordinated workers. Every daemon exports Prometheus metrics, so the whole fleet reads as one Grafana page.

Shared memory is 50× faster and we still didn't take it, because the daemon is only consulted once per shard, not once per sample. Amortized over the hundreds of thousands of records inside a 10 GiB shard, a 6 µs round trip rounds to zero, and the kernel cleaning up dead clients for free is worth more than the microseconds. Measured end to end from the Python client under a 20‑process flood: p50 74 µs, p99 about 1 ms, 124,000 requests/s.

05 · Memory

One gigabyte in RAM, not one hundred

Getting the shard onto NVMe settles downloads and leaves the memory problem standing. Say 100 workers on one node each need scattered lines of the same 1 GiB annotation shard. There are two obvious ways to do that, and each fails in its own way.

Load the file. Each worker parses the whole JSONL into a dict at startup. Lookups are then instant, but processes can't share heap objects, so that's 100 private copies of the same gigabyte: 100 GiB of RAM and a long stall at the start of every job, for 1 GiB of data.

Don't load it. Keep nothing in memory and read each record straight off the drive by its byte offset. Memory is now flat, and every single lookup has become a disk seek: a median of 297.6 µs per record, paid millions of times, with 100 workers queuing behind one device.

What processes do share is the kernel's page cache, and that's the third option. The first time a JSONL shard is touched, the daemon warms it — one madvise POPULATE_READ call telling the kernel to pull the whole file resident. Workers keep reading by offset, exactly as in the second option, except the pages are already in RAM. One copy of the gigabyte, and every read served from memory.

And for images?

We ran the same experiment on image TARs and it bought nothing: every warming mode landed within 1.5% of not warming, because an image read spends its ~15 ms in JPEG decode and almost none of it waiting on the drive. So the shipped policy is asymmetric. Annotations always warm; images never do. That's also why a 10 GiB image shard is comfortable, since it only ever needs to sit on NVMe, never in RAM.

The full warming numbers side note

Three modes were benchmarked on both shard types: no warming, WILLNEED (async posix_fadvise hint, returns immediately) and POPULATE_READ (blocks until every page is resident).

The blocking warm itself costs about 0.5 s on a 1 GiB JSONL and about 5 s on a 10 GiB TAR, which is the other reason images skip it: five blocked seconds for a 1.5% change is a bad trade. Warmed pages aren't pinned; they're ordinary evictable page‑cache pages, so the daemon only trusts a completed warm for a few seconds before it will re‑warm on request. The benchmark also caught a bug: 64 concurrent warms of the same shard were up to 11.7× slower per call until the daemon learned to deduplicate them.

06 · The fast path

Then stop calling the daemon

One last trick makes the steady state almost free. The client never asks permission before reading; it opens the local path as if it must exist, and only a FileNotFoundError sends it to the daemon. For any shard, that means only the first few concurrent workers ever pay the socket round trip. Every subsequent read, from every process, for the rest of the run, is an open and a pread against a warm page cache with the daemon left out entirely.

The daemon is only on the miss path. Once a shard is resident, reads go straight to the page cache and the socket is never touched again.

In steady state the client does nothing a plain local read wouldn't do: the open succeeds, the pread runs, and the daemon is never involved.

07 · Portability

The parts you can swap

Nothing outside the daemon knows where shards come from. "S3" throughout this post is one configuration of a single download routine inside patramd, which shells out to rclone, and rclone speaks every major object store. Move clouds, or move to on‑prem storage, and you change that one routine on one daemon per node; every training loop, data pipeline and URI in the company keeps working untouched.

The daemon itself is about 2,500 lines of Go.

Why Go, and not Python or Rust side note

Python fell to the GIL: downloads, socket handling and madvise calls all fighting for one core puts a hard ceiling on a daemon serving 50+ containers. Rust fell to economics rather than performance; its advantage here is losing Go's ~100 µs GC pauses, which are invisible next to a 200 ms S3 download, and it charges for that in development and maintenance time. Go was built for exactly this shape of program: a small, long‑running network service with many cheap concurrent connections.

08 · Production

How it's held up

Patram‑FS runs on every node of our training fleet, with each daemon's metrics scraped into one dashboard. It's load‑bearing beyond training too, which was the point of protecting the per‑sample address: a teammate's dataset‑construction pipeline installs the same client library and addresses 12.9 million OCR records by patram:// URI, sharing each node's cache with whatever training job happens to be running there.

Training without the shared filesystem

A 7B model trained on about 8 billion tokens on 128 GPUs, reading every sample from local NVMe and S3.

The fleet also has a shared FSx Lustre filesystem, and before Patram‑FS every training job read its data from it. That mount is shared by every node and every team, so one job's read pattern shows up as latency for everyone else.

For this run the shards lived in S3, each node's daemon pulled the shards it needed onto local NVMe, and the training loop read them from there. FSx was never on the data path. That is the property the system was built for: training I/O stops touching the shared filesystem.

The obvious question is why not use an off‑the‑shelf streaming‑dataset library. Those hand your loader a stream of samples, which means the loader has to be written their way, and the samples have to be encoded into their record format first. Patram‑FS keeps the per‑sample address instead. Every dataloader ever written against "one sample, one path" works against a URI unchanged, and a URI can sit in a manifest, a Parquet column or a config the same way a path could.

The read path is also shorter. An uncompressed TAR member needs no decoding step of its own, so there's no unpack, no decompress and no conversion between the drive and your tensor — just pread at whatever the device gives you. The only latency anywhere in the system is the first download of a shard, and since ensure_shard can be called for a shard you haven't reached yet, that download overlaps with training you're already doing.

Where it earns its keep

  • Many uncoordinated processes on one node reading the same data: training ranks, data jobs, notebooks share one cache.
  • Codebases written against "each sample has its own path," kept working with a one‑line change.
  • Reads at raw pread speed; no FUSE layer, no decompression, no per‑read daemon hop.
  • Any object store behind one swappable download routine.

Sharp edges we chose

  • It isn't a filesystem. You can't ls the dataset.
  • A sampler that jumps uniformly across every shard defeats the cache. Each miss pulls another 10 GiB shard down and evicts one that's still in use, and taken to its limit the node ends up trying to hold the entire dataset on NVMe. Sampling has to keep some shard locality to stay cheap.
  • It's our own infrastructure to run. A stopped daemon still serves every shard already on the node, but nothing new arrives until it's back.

09 · Takeaways

If you're building something like this

  • Pack tiny samples into big uncompressed shards, but preserve a per‑sample byte address.

    The address is what lets every existing codebase keep working with a one‑line change.

  • Put node‑wide coordination in one process that stays off the data path.

    A daemon that never carries bytes can't bottleneck anything, and one daemon per node turns dedup, rate control and monitoring into local problems with one owner.

  • The kernel's page cache is already a shared memory system.

    Warm a file once and every process on the node reads it at RAM speed; you don't need to build the sharing layer, only to trigger it.

  • Benchmark defaults per data type.

    The identical warming trick was a 2.6× win on JSON and a rounding error on JPEGs, because an annotation read waits on the drive and an image read waits on JPEG decode.
